## 1. 文档说明

本文档为「商户创建 → 商户登录 → 商品提审 → 平台审批 → 上架生效」闭环流程定义**完整可执行/可回归的测试用例**。用例与自动化脚本逐一对应：每个阶段（A/B/C/D）对应一个 `phase_*.py`，其截图文件名即用例的证据输出。

用例按**手机视口（390×844，deviceScaleFactor=2）**驱动真实界面抓取，截图所见即所得。

### 1.1 用例编号规则

| 前缀 | 含义 | 对应脚本 | 截图段 |
|------|------|----------|--------|
| `TC-A` | 阶段 A：平台超管创建商户 | `phase_a.py` | `m01`~`m07` |
| `TC-B` | 阶段 B：商户登录 + 商品提审 | `phase_b.py` | `m08`~`m15` |

优先级：P0 = 流程主链路（必须通过）；P1 = 关键分支；P2 = 次要项。

## 2. 前置条件（测试环境准备）

- [ ] 平台超管账号具备「租户管理」「商品上架审批」菜单权限。
- [ ] 后台 Admin API 可达 `https://e.joho.cn/admin-api`，能登录超管。
- [ ] 目标渠道（新建租户渠道）已配置默认税务区域（脚本会自动设置）。
- [ ] 本地已安装 Python3 + `playwright`（chromium），脚本目录可写 `shots/`。

> **幂等说明**：阶段可重复执行。若渠道下已存在同名商品的 pending 记录，phase_b 会复用最新一条，不重复创建（避免污染数据）。

## 3. 阶段 A：平台超管创建商户（`phase_a.py`）

- **前置**：数据库有超管账号。

- **预期**：进入后台工作台，无需登录干预。截图 `m01_login.png`。

## 7. 状态流转与判定标准

| `marketplaceStatus` | 界面显示 | 触发动作 | 判定 |
|---------------------|----------|----------|------|
| `null` | 待提交 | 商户创建商品但未提交 | ✅ 正常 |
| `pending` | 已提交，待审核 | 商户「提交上架」 | ✅ 正常 |
| `approved` | 已在默认站点上架 | 平台「通过」 | ✅ 闭环完成 |
| `rejected` | 已驳回 | 平台「驳回」（含原因） | ✅ 分支 |

**P0 用例全部通过** 即视为该流程回归验收通过。

## 8. 回归执行指引

1. 在 `docs/demo/playwright/` 目录下依次执行：
   ```bash
   python phase_a.py   # 创建租户 + 管理员 + 取初始口令
   python phase_b.py   # 商户登录 + 建商品 + 提交上架
   python phase_c.py   # 平台审批
   python phase_d.py   # 商户复看
   ```
2. 每次执行后核对 `shots/` 下新增/更新的截图是否为 390×844（手机视口）输出。
3. 若报错可查看：税区未设（重跑 phase_b 自动补设）、缓存元数据失效（重新生成 `meta_phase_a.json`）、同名 ambient 冲突（幂等复用）。
4. 截图更新后，同步到 web-admin 静态目录并重新构建部署（见 §9）。
