# 虚拟库存与物理库存模型 设计文档（方案 2-A）

> **方案标识：方案 2 子项目 A（库存模型）**。方案2 拆 4 子项目按序设计：A 库存模型 → B 物流配送 → C 对账 → D 详情页展示。
> **存续：本文为设计定稿，写入后随方案2 各子项目一并存档，待多方案比选后统一执行（暂缓实施）。**

## 1. 目标与范围

在既有 Vendure 原生多仓库库存体系（inventory-plugin 已基于 `StockLocation`/`StockLevel`/`StockMovement` 实现进销存全链）之上，引入**虚拟库存**与**物理库存**模型：

- **虚拟库存**：网络销售对外展示的可售数。
- **物理库存**：真实仓库库存，同一变体可分布多个物理仓。
- 二者关系：**物理为准，虚拟为同步镜像**。开启物理库存的租户，其（绑定物理仓的）变体虚拟库存 = Σ绑定物理仓库存。

本方案仅覆盖库存模型层（A）；物流（B）、对账（C）、详情页展示（D）为后续独立子项目，本文只预留数据源与衔接点。

## 2. 已确认决策

1. 驱动关系：**物理为准，虚拟=同步镜像**。未开启物理时虚拟仓独立可售；开启后绑定物理仓的变体，其虚拟 onHand 始终与 Σ物理 onHand 同步。
2. 默认仓库 = **租户编码命名的物理仓**（`{tenantCode}`）。网络订单在未建多仓前默认从该默认仓扣减；多仓后支持默认/就近/指定分配。
3. 商品粒度：**按商品（变体/SKU）混合**。同一租户内「纯虚拟（独立可售）」与「物理驱动（绑定多仓，虚拟=Σ）」可并存。
4. 实现路径：**纯 Vendure 原生映射**（虚拟仓=一个 StockLocation；物理仓=StockLocation；复用 StockLevel/StockMovement/进销存，零新表，仅加镜像同步器）。

## 3. 数据模型与仓库体系

**仓库（StockLocation）两类性质**（StockLocation customFields `kind`）：
- **虚拟仓**：`code={tenantCode}-virtual`，`visibleInChannel=true`（网络渠道可售源）、不可真实发货。每租户一个，懒创建。
- **物理仓**：`visibleInChannel=false`（不直接对外可售，由虚拟镜像对外），含坐标 `lat/lng` 供就近。
  - 默认仓 `code={tenantCode}`（开启物理时自动创建，onHand 初始 0）
  - 附加仓 `code={tenantCode}-{alias}`

**商品-物理仓绑定**（变体/SKU 粒度）：
- 新关联表 `VariantLocationBinding`：`{variantId, locationId, isDefault}`。
- 物理驱动变体：绑定 1~N 物理仓（含默认仓）；其虚拟仓 onHand=Σ绑定物理仓。
- 纯虚拟变体：无 binding，仅虚拟仓有 StockLevel（独立可售数；即既有原库存位置，完全兼容旧数据）。

**口径**：开启物理库存 = 该租户获得物理仓能力（自动建默认物理仓），不影响既有纯虚拟商品。「虚拟=Σ物理」精确到**绑定了物理仓的变体**：虚拟库存 = Σ绑定物理仓 onHand。

## 4. 同步镜像机制

- **统一切口（修正为事件级）**：挂 `StockMovementEvent` **阻塞处理器**。对每个产生 onHand 变动的事件（SALE 发货、StockAdjustment 入库/盘点/校准/出库、退货、撤销发货等）：
  - 若该变体为物理驱动 且 涉及物理仓 → 重算 Σ 绑定物理仓 onHand → `adjustStockForLocation` 写虚拟仓 StockAdjustment + ledger `biz='mirror'`。
  - 写入与扣库/账本**同一 DB 事务**（阻塞处理器运行在被订阅业务事务内），原子生效或全无，失败即回滚。
- **防递归**：镜像写虚拟仓按虚拟仓 locationId 进入，仅对物理仓源重算，天然无 A↔V 互触发。
- **初始化**：开启物理 → 自动建默认物理仓（onHand=0）。既有纯虚拟商品不迁移。首次绑定变体到物理仓时，可选项：把该变体当前虚拟库存量迁入默认物理仓。删除所有 binding → 变体回落纯虚拟，**保留当前镜像值**转独立虚拟库存（不外溢损失）。

## 5. 销售扣减与分配

- **自定义 StockAllocationStrategy**：下单分配时，物理驱动 → 目标=绑定物理仓（单仓=默认仓；多仓=默认/就近）；纯虚拟 → 目标=虚拟仓（现状行为不变）。写 Allocation 记各目标仓 allocated 量，onHand 不动。
- **扣减时序**见 §5.1 增补——发货才真扣 onHand（既有 Vendure 语义），镜像随事件同步。
- **缺货**：所需仓 onHand<需求按既有缺货拦截，不自动跨仓挪用（多仓凑货留待后续，YAGNI）。

### 5.1 库存扣减与回滚具体逻辑（增补）

**扣减时序（物理驱动变体）**
```
① 下单支付   → 自定义分配策略分配（目标=绑定物理仓，写 Allocation）
② 发货(fulfill) → core 对各 Allocation 目标仓产生 Sale，真扣 onHand
③ 阻塞处理器(StockMovementEvent 统一) 同事务:
      a) 写 order:out 账本（既有 recordOrderSalesOut）
      b) 变体物理驱动且涉物理仓 → 重算 Σ绑定物理仓 → 同步虚拟仓(+ledger mirror)
      c) 任一失败抛错 → 整事务（含 core 扣库）回滚
```
纯虚拟变体与现状一致（分配到虚拟仓，发货扣虚拟仓）。

**回滚/补偿**
| 场景 | 动作 | 镜像 |
|---|---|---|
| 同事务内失败 | 事务整体回滚 | 随回滚，无残留 |
| 订单取消/部分取消（未发货） | ReleaseAllocation 恢复 allocated，onHand 未动 | 无需处理 |
| 发货后退回/退款 | 既有 `applyAfterSalesRestockMulti` 按 Allocation 逐仓回补 onHand | 同事务触发镜像重算 |
| 撤销发货(Unfulfill) | 回滚 Sale 恢复 onHand | 镜像自动回算 |
| 改默认仓/删 binding | 变体物理驱动开关随变 | 回落纯虚拟时保留当前镜像值转独立虚拟 |

**一致性**：扣 onHand + 账本 + 镜像同一 DB 事务；mirror 账条标记供 C 对账识别忽略；负库存沿用既有校验。

## 6. 库存查询数据源（衔接 D）

店铺端每变体返回：
- `saleableStock`（对外展示数）= 虚拟仓 onHand（物理驱动时即 Σ，纯虚拟独立）
- `stockDetail`（物理驱动才有）= 各绑定物理仓 `{locationId, 名称, 坐标, onHand}` + 按客户地址的距离/就近排序

复用既有「就近库存」接口（inventory-shop.resolver）扩展。

## 7. 边界与不破坏原则

- 虚拟仓每租户唯一（kind=virtual）；物理仓 code 唯一（tenantCode / tenantCode-alias），重复创建报错。
- 镜像同事务写，无中间态。
- 未启用本功能的租户/变体完全走旧路径（虚拟仓即原库存位置），**零表结构破坏、不迁移既有数据**。
- 就近排序无坐标仓库排后。
