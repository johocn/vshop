## 1. 背景与目标

M2 券商城联调（8.1/8.2）已验证：领券、购券目录、余额支付闭环、加价购全链路。盘点结论（bs-1~bs-3）：

- **代码全齐、界面全齐**：到店核销（web-admin `in-store/`）、券包（`coupon/bundle*`）、定向发放（`coupon/issue`）、券包购买、卡包出示券码——前后端能力均已实现并有管理界面，但**从未端到端上线验证**。
- **唯一硬缺口**：微信支付商户证书未配置（生产报 `PEM: no block`），材料存于 PaymentMethod handler args（存库），admin-api 可直接配置。

**本轮目标（用户已确认）**：交易闭环优先，范围 = 验证闭环 + 证书。即端到端联调到店核销/券包/定向发放三条链路，并完成微信支付证书配置与小额真实支付验证。

## 2. 方案选择

| 方案 | 内容 | 结论 |
|------|------|------|
| **A. 线上一步到位（选定）** | 探测线上→配测试数据→端到端联调→证书配置→交付 | 生产环境真实闭环，一次收口 |
| B. 本地起后端联调 | 本地 vendure + SQLite 复现 | 否：证书/微信支付无法本地验证，联调结果不代表线上 |
| C. 只补证书不联调 | 最小范围 | 否：核销/券包/发放从未验证，风险后移 |

## 3. 五阶段设计

### 阶段③ 端到端联调（核心）

#### 3.1 到店核销主链路（TC-IS-1，P0）

```
C端领券(claimCoupon) → 卡包出示券码(QR) → web-admin 扫码/输码
  → inStoreBillQuote(券码, 金额) → 报价确认
  → inStoreBillRedeem(券码, 金额, 备注) → 核销 ok · 券置 USED · 落流水
  → C端卡包刷新「已使用」 + web-admin 流水/汇总页核对（笔数·原价·优惠·实收）
```

#### 3.3 执行方式（延续 8.2 经验）

- C 端与 web-admin 均**真实点击**操作；GraphQL 直发仅用于准备数据与结果校验，不替代 UI。
- 已知工具限制：JS 赋值不触发 uni-app radio/v-model（支付方式、兑换码输入），必要时用「接口直发 + 真实点击」混合路线。
- 商品详情页路由参数为 `slug`（非 `id`）。

### 阶段④ 微信支付证书配置

| 步骤 | 内容 |
|------|------|
| 1. 材料交付 | 用户提供 5 项：商户号 `mchId`、商户 API 私钥 `apiclient_key.pem`、证书序列号 `serialNo`、APIv3 密钥（32位）、微信平台公钥 PEM。**走本地文件**（`e:\zhao\vshop\.secrets\`，gitignore 覆盖），不进 git、不留在对话记录 |
| 2. 写入配置 | admin-api `paymentMethods` 查询 → 定位 wechatpay handler → `updatePaymentMethod` 写入 handler args（mchId / privateKey / serialNo / APIv3 key / 平台公钥）。**存库，非环境变量**（wechatpay-handler.ts L77-81 取用） |
| 3. 小额验证 | H5 购券 74「TEST·无门槛减5元券」（¥1）→ 微信真实拉起收银台 → 用户真机完成支付 → 轮询 PAID → 发券。需用户真机配合一次 |
| 4. 失败兜底 | 按报错三类定位：`PEM: no block`=私钥缺失/格式错；签名错误=APIv3 key 或 serialNo 错；证书链错误=平台公钥错 |

## 5. 风险与回退

| 风险 | 缓解 |
|------|------|
| 线上 web-admin 缺页 | 阶段①即探测，缺则本地构建部署（deploy.mjs 路线成熟） |
| 核销幂等缺陷（资损） | TC-IS-3 独立 P0 验证；发现即回退该功能入口（不阻断其余链路） |
| 证书材料格式错误 | 阶段④步骤 4 三类报错对照表定位；材料走文件避免复制走样 |
| 微信拉起需真机 | 单点依赖用户配合一次；其余验证不阻塞 |
| 测试数据残留 | 全部 TEST 前缀 + enabled 可开关，8.2 已建立禁用惯例 |
